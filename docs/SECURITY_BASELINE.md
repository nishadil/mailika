# Security Baseline

Mailika targets OWASP ASVS 5.0 Level 2 for the web application. Use [Threat Model](THREAT_MODEL.md), [Data Handling](DATA_HANDLING.md), and [ASVS Release Gate](ASVS_RELEASE_GATE.md) before tagging a release candidate.

## Required Production Controls

- `APP_ENV=production`
- `APP_DEBUG=false`
- Strong random `APP_KEY` generated by `php bin/mailika-key`
- `SESSION_SECURE_COOKIE=true`
- HTTPS with HSTS at the edge
- `MAILIKA_TRUSTED_PROXIES` set to the exact reverse proxy IPs/CIDRs when TLS terminates before PHP
- TLS-valid IMAP and SMTP
- `MAILIKA_REQUIRE_TLS=true`
- Restricted `MAILIKA_ALLOWED_IMAP_HOSTS`
- Restricted `MAILIKA_ALLOWED_SMTP_HOSTS`
- Restricted `MAILIKA_ALLOWED_SIEVE_HOSTS` when ManageSieve publishing is enabled
- Restricted `MAILIKA_ALLOWED_LDAP_HOSTS` when LDAP directory search is enabled
- Centralized logs with secret redaction
- Sanitized database-backed audit events for security-relevant actions
- Redis-backed sessions and rate limits for multi-node deployments
- Regular `composer audit`, `npm audit`, local secret scanning, release metadata inventory checks, CodeQL, dependency review, and container scans
- GitHub Actions workflows with explicit permissions, job timeouts, concurrency controls, versioned action references, no `pull_request_target`, and checked release-gate inventory

`php bin/install` and `php bin/upgrade` enforce the runtime subset of these controls when `APP_ENV=production`, including HTTPS application URL, secure session cookies, non-debug mode, TLS-required mail connectors, non-fixture IMAP adapter, restricted host allowlists, and valid TCP ports for configured IMAP, SMTP, ManageSieve, and LDAP endpoints.

Dynamic webmail responses default to `Cache-Control: no-store`, `Pragma: no-cache`, and `Expires: 0` so mailbox pages, JSON responses, and error pages are not retained by shared or browser caches. Routes that intentionally set their own cache policy keep that policy.

When `MAILIKA_RATE_LIMIT_STORE=redis`, Redis is the authority for login throttling. If Redis is unavailable, Mailika fails closed and rejects sign-in attempts instead of falling back to node-local throttling.

## Email Rendering

HTML messages must pass through `HtmlSanitizer`. Remote images are blocked by default. Active content, event handlers, forms, embedded frames, and unsafe CSS are not allowed.

Remote image loading can be enabled per mailbox preference, but it remains disabled by default.

Known `cid:` references for inline image MIME parts are rewritten to authenticated Mailika attachment URLs before sanitization. Unknown `cid:` references and remote image URLs are stripped unless remote image loading is explicitly enabled.

Attachment download names and MIME types are sanitized before response headers are built. Mail-server-provided filenames cannot inject headers, preserve path traversal segments, or force unsafe content types; inline rendering is only allowed for MIME parts marked inline with a safe raster image content type. Active downloaded formats such as HTML, SVG, XML, and JavaScript are served as `application/octet-stream`. Mailika blocks attachment downloads that exceed `MAILIKA_MAX_ATTACHMENT_BYTES`. Attachment responses use a sandboxed content security policy and `X-Download-Options: noopen`.

## Session Credentials

Mailbox credentials, mailbox identity, and IMAP/SMTP connection metadata are sealed together with Sodium authenticated encryption before being placed in server-side session data. Session IDs are regenerated after login and destroyed on logout.

Account profiles are non-secret metadata only. They may store mailbox addresses and IMAP/SMTP host settings, but they never store mailbox passwords or session tokens.

Forwarded HTTPS headers are ignored unless the immediate proxy address matches `MAILIKA_TRUSTED_PROXIES`; direct HTTPS still works without proxy configuration.

Login rejects unknown SMTP security modes. When `MAILIKA_REQUIRE_TLS=true`, SMTP must use `starttls` or `smtps`; `none` is allowed only in explicit non-TLS development or test deployments.

ManageSieve publishing is disabled by default. When enabled, `MAILIKA_SIEVE_REQUIRE_TLS=true` requires `starttls` or implicit `tls`, hostnames are checked against `MAILIKA_ALLOWED_SIEVE_HOSTS`, and TLS peer verification is enabled before mailbox credentials are sent with SASL PLAIN.

LDAP directory search is disabled by default. When enabled, `MAILIKA_LDAP_REQUIRE_TLS=true` requires `starttls` or implicit `tls`, hostnames are checked against `MAILIKA_ALLOWED_LDAP_HOSTS`, and bind credentials remain server-side configuration. Audit events record directory name, query length, and result count, not the searched text.

## Sender Identities

Compose requests may only send from the authenticated mailbox address or identities stored for that mailbox. Posted sender values are checked server-side before SMTP delivery, and configured Reply-To metadata is carried from the trusted identity record.

Outbound recipient, identity, Reply-To, contact, and imported vCard addresses are normalized through one validator. Internationalized domains are converted to IDNA ASCII form before storage or delivery. Unicode local-parts are accepted for SMTPUTF8-capable servers and are explicitly flagged on the send envelope; if the SMTP server rejects SMTPUTF8, Mailika returns a safe user-facing delivery error without exposing SMTP credentials or server internals.

Mailika does not provide OpenPGP encryption or signing yet. Compose blocks OpenPGP private-key armor in message bodies and validated attachments so users do not accidentally save or send private key material through drafts or SMTP. Attachment checks stream the full validated file with overlap so armor is detected beyond the file prefix and across read boundaries.
