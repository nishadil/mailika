# Operations

Mailika can run behind Nginx, Caddy, Apache, or any reverse proxy that forwards requests to PHP-FPM.

Review [Data Handling](DATA_HANDLING.md) before changing persistence, logs, metrics, caches, exports, uploads, backups, or monitoring integrations.

## Health

`GET /healthz` returns JSON with basic application liveness. `GET /readyz` checks runtime readiness, configured data-store driver availability, Redis readiness when configured, and writable storage paths. Neither endpoint validates user mailbox connectivity or exposes secrets.

`GET /metrics` returns Prometheus-style text metrics for runtime build labels, readiness, and boolean readiness checks. Metrics are intentionally low-cardinality and must not include mailbox addresses, credentials, message metadata, database hosts, or user input.

Mailbox list metadata is cached in `message_metadata_cache` after successful IMAP reads. If IMAP is temporarily unavailable, Mailika can show cached envelopes for the selected folder/search while clearly marking the mailbox view as cached. Message bodies and attachment contents are not stored in this cache. Read/unread, flag, move, copy, archive, and delete actions update cached envelopes after the mail server accepts the action, and each folder cache is bounded to 10,000 envelope rows.

Mailbox searches support plain text plus structured operators: `from:`, `to:`, `subject:`, `is:unread`, and `is:flagged`. Quoted subject values are accepted for multi-word subjects. Saved searches store the canonical operator string, while the cache fallback can apply envelope-safe filters such as sender, subject, unread, and flagged state when live IMAP is temporarily unavailable.

Compose uploads support multiple attachments. Bound them in production with `MAILIKA_MAX_ATTACHMENTS`, `MAILIKA_MAX_ATTACHMENT_BYTES`, and `MAILIKA_MAX_ATTACHMENT_TOTAL_BYTES`; PHP and reverse-proxy upload limits must be at least as strict as the Mailika limits. Downloaded mailbox attachments are also checked against `MAILIKA_MAX_ATTACHMENT_BYTES` before Mailika serves them.

The primary IMAP adapter checks server-reported attachment sizes before loading attachment content when metadata is available. The controller still validates the actual response bytes before serving the download, so incorrect or missing server size metadata remains bounded by Mailika's download policy.

Restrict mailbox endpoints in production with `MAILIKA_ALLOWED_IMAP_HOSTS` and `MAILIKA_ALLOWED_SMTP_HOSTS`. Leave `MAILIKA_REQUIRE_TLS=true` so IMAP requires TLS and SMTP accepts only `starttls` or `smtps` during login.

Display preferences store locale, timezone, remote-image policy, theme, threaded-listing preference, and mailbox page size. Before sign-in, the layout negotiates a supported locale from `Accept-Language` and falls back to English for unsupported or malformed values. Run `php bin/upgrade` after releases so database deployments receive new preference columns before users save settings.

Mail filter rules are stored as Mailika-owned local Sieve definitions and can be reviewed as a generated script preview. Set `MAILIKA_SIEVE_ENABLED=true`, `MAILIKA_SIEVE_HOST`, `MAILIKA_SIEVE_PORT`, `MAILIKA_SIEVE_TLS=starttls`, and `MAILIKA_ALLOWED_SIEVE_HOSTS` to allow users to publish the generated script to a ManageSieve server. Leave `MAILIKA_SIEVE_REQUIRE_TLS=true` in production. Mailika uploads the configured `MAILIKA_SIEVE_SCRIPT_NAME` and sets it active after the server accepts the script.

Before uploading, Mailika reads the existing server script with `GETSCRIPT`. It only overwrites an absent script or a script containing Mailika's generated marker, and refuses to replace externally edited scripts.

The filters screen can inspect a pasted existing Sieve script and summarize required extensions, detected actions, Mailika ownership, and unsupported constructs. Scripts generated by Mailika can be imported back into editable local rules. Arbitrary external scripts remain inspection-only because Mailika cannot safely preserve unsupported Sieve constructs yet.

LDAP directory search is disabled by default. To expose read-only directory lookup on the contacts screen, set `MAILIKA_LDAP_ENABLED=true`, `MAILIKA_LDAP_HOST`, `MAILIKA_LDAP_BASE_DN`, and `MAILIKA_ALLOWED_LDAP_HOSTS`; keep `MAILIKA_LDAP_TLS=starttls` or `tls` with `MAILIKA_LDAP_REQUIRE_TLS=true` in production. Bind credentials are server-side configuration only and are never stored per mailbox.

Account profiles store only non-secret connection metadata for multi-account workflows. Saved profiles are available from the mailbox sidebar and can prefill the next sign-in form with email, host, port, and TLS choices, but Mailika never stores or replays IMAP, SMTP, or ManageSieve passwords.

When a production IMAP server advertises `ACL`, Mailika reads the current folder's `MYRIGHTS` response, shows the user's mailbox rights in the mailbox status row, lists `GETACL` shared-access entries, and suppresses unsupported write/delete/folder actions in the UI and POST handlers. Users with the IMAP administer right can update or revoke ACL entries with `SETACL` and `DELETEACL`; the mail server remains the final authority for permission changes.

## Redis

File-backed sessions and rate limits are acceptable for single-node local deployments. Multi-node production deployments should set `SESSION_DRIVER=redis`, `MAILIKA_RATE_LIMIT_STORE=redis`, `REDIS_SESSION_DSN`, and `REDIS_DSN`. Supported DSN schemes are `redis://`, `rediss://`, `tcp://`, and `tls://`; use `rediss://` or `tls://` when Redis is outside a trusted private network.

`/readyz` checks both Redis extension availability and Redis reachability when either Redis-backed sessions or rate limits are configured. The rate limiter fails closed if Redis is configured but unavailable, so sign-in attempts are rejected instead of bypassing shared throttling.

## Upgrades

1. Back up the database.
2. Deploy the new image or release artifact.
3. Run `php bin/upgrade`.
4. Warm caches if configured.
5. Verify `/healthz`, `/readyz`, and a test mailbox login.

`php bin/upgrade` runs a preflight check before migrations. It verifies the PHP runtime and required extensions, confirms the configured PDO database driver is loaded, rejects writable public storage paths, creates missing storage directories, and rejects invalid configured TCP ports. It does not require a local `.env` file or `APP_KEY`, so container deployments can continue to provide configuration through the environment.

When `APP_ENV=production`, install and upgrade preflight also enforce the production security posture: `APP_DEBUG=false`, `APP_URL=https://...`, `SESSION_SECURE_COOKIE=true`, `MAILIKA_IMAP_ADAPTER` not set to `fixture`, `MAILIKA_REQUIRE_TLS=true`, restricted IMAP/SMTP allowlists, and restricted TLS-required Sieve/LDAP allowlists when those optional connectors are enabled.

Use [Backup And Restore](BACKUP_RESTORE.md) for PostgreSQL dump/restore commands and rollback notes.

## Installation

Use `php bin/install` after `.env` is configured. The installer runs the same runtime, storage, network-port, and production-security preflight as upgrades, additionally requiring a local `.env` file and a valid `APP_KEY` generated by `php bin/mailika-key`. It refuses to continue if writable storage has accidentally been placed under `public/`.

## External Mail Fixtures

The `mail-fixtures` Compose profile starts GreenMail for optional IMAP/SMTP integration testing. It exposes SMTP on `3025`, IMAP on `3143`, and the GreenMail API on host port `8081`.

```bash
docker compose --profile mail-fixtures up -d greenmail
composer fixtures:check -- mail
composer test:external-mail
docker compose --profile mail-fixtures down
```

The same readiness and test commands can target a non-Compose disposable fixture when SMTP and IMAP are already reachable on the configured ports. Override `MAILIKA_TEST_MAIL_HOST`, `MAILIKA_TEST_SMTP_PORT`, and `MAILIKA_TEST_IMAP_PORT` when the fixture is not on `127.0.0.1:3025/3143`.

This fixture is for tests only. Production deployments should use `MAILIKA_IMAP_ADAPTER=webklex` with real TLS-valid IMAP/SMTP services.

## External ManageSieve Fixtures

The `sieve-fixtures` Compose profile starts a disposable Dovecot/Pigeonhole service for optional ManageSieve publishing tests. It exposes ManageSieve on `4190` and IMAP on `31143`.

```bash
docker compose --profile sieve-fixtures up -d managesieve
composer fixtures:check -- sieve
composer test:external-sieve
docker compose --profile sieve-fixtures down
```

The default fixture account is `user@example.com` with password `secret`, matching the test defaults. To point the same test at another fixture, configure it with:

- `MAILIKA_TEST_SIEVE_HOST`, default `127.0.0.1`
- `MAILIKA_TEST_SIEVE_PORT`, default `4190`
- `MAILIKA_TEST_SIEVE_TLS`, one of `none`, `starttls`, or `tls`
- `MAILIKA_TEST_SIEVE_EMAIL` and `MAILIKA_TEST_SIEVE_PASSWORD`
- `MAILIKA_TEST_SIEVE_SCRIPT_NAME`, default `mailika-test`

The fixture account must allow SASL PLAIN and `PUTSCRIPT`/`SETACTIVE`. Use a disposable test account because the script named by `MAILIKA_TEST_SIEVE_SCRIPT_NAME` can be replaced when it already carries Mailika's generated marker. The bundled Compose fixture disables TLS and cleartext-auth restrictions by design; never reuse it as a production mail server.

When Docker is unavailable, run the disposable PHP protocol fixture in one shell:

```bash
php tests/fixtures/managesieve/server.php --host=127.0.0.1 --port=4190
```

Then point the same readiness/test commands at it from another shell:

```bash
composer fixtures:check -- sieve
composer test:external-sieve
```

The PHP fixture is intentionally narrower than Dovecot/Pigeonhole. It validates Mailika's ManageSieve `AUTHENTICATE`, `GETSCRIPT`, `PUTSCRIPT`, `SETACTIVE`, and `LOGOUT` flow without proving compatibility with a full mail-server suite.

## Containers

The default image is intended for GHCR as `ghcr.io/nishadil/mailika`. Runtime containers should run as a non-root user and mount persistent storage for sessions, cache, logs, and uploads.

The Compose example mirrors the production posture with a read-only application filesystem, dropped Linux capabilities, `no-new-privileges`, a small `/tmp` tmpfs for PHP upload handling, a named `mailika-storage` volume for application runtime state, and health-gated Postgres/Redis dependencies. Keep writable mounts scoped to `storage/` and database volumes.

Images are published from the `main` branch and `v*` tags. Branch builds publish `main`, `latest`, and `sha-*` tags; release tags publish semantic-version tags such as `1.0.0` and `1.0`. The publish workflow scans the image before pushing and emits registry SBOM/provenance attestations.

```bash
docker pull ghcr.io/nishadil/mailika:latest
```

## Public Document Root

Only `public/` should be served by the web server. Writable paths such as `storage/logs`, `storage/sessions`, `storage/uploads`, application source, Composer metadata, and environment files must never be reachable under the public document root. Sample Nginx and Caddy rules live in `config/webserver/`.
